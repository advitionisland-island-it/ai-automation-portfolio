# ケーススタディ：人の承認を挟むAI営業オペレーション

[English](case-study.md) | 日本語 | [日本語README](../README.ja.md)

> ポートフォリオプロジェクトP01の説明です。実顧客への導入事例ではありません。合成データを使い、実測結果と未検証の範囲を分けて記載しています。

## 課題

B2Bの問い合わせには、内容を読み、見込み度を判断し、最初の返信を作る作業が必要です。受付の重複や、未確認のAI文章の送信は信用を損ねます。

このプロジェクトでは、評価と返信案の作成を自動化しながら、**最終的に送る本文を人が確認する**仕組みを作りました。単にLLMを呼ぶことに加え、入力検証、重複防止、状態管理、障害回復を実装しています。

## 想定する導入前の状態

共有メールボックスや表計算で問い合わせを受け取り、担当者が手作業で分類して返信する運用を想定しています。実際の企業の業務を測った結果ではありません。処理時間の削減率、売上への効果、顧客満足度の改善は測定していません。

## 構成

フォーム → n8n W1 → FastAPI → PostgreSQL → workerでの評価・下書き → 人の承認 → Mailpitへの送信、という流れです。n8n W2が承認依頼を、W3が障害通知を届けます。[日本語READMEの構成図](guide.ja.md#構成と処理の流れ)

Mailpitはローカルのメール受信サービスです。ここでの「送信」は、外部の顧客にメールを配送したという意味ではありません。

## この設計を選んだ理由

### n8nは連携、Pythonは判断を担当する

n8nはWebhook、定期実行、通知を担当します。入力の妥当性、重複、状態遷移、承認の意味はPythonにまとめ、実DBを使うテストで確認します。業務判断をworkflowの各所へ分散させないためです。[ADR原文](adr/0001-n8n-python-boundary.md)

### PostgreSQLに状態とジョブをまとめる

`FOR UPDATE SKIP LOCKED`とleaseで、複数workerと処理中の停止に対応します。リードの状態変更と、それによって発生するジョブを同じトランザクションで保存できます。この規模ではRedisやCeleryを追加せず、一つのDBで構成しています。

### AIの提案を規則で検証する

LLMはスコア、理由、要約、確信度を返します。スコアからhot / warm / coldへ分類する規則と、人へ確認を回す条件はPythonに置きます。回答の型、範囲、制御文字などを検証し、不正な出力を評価テーブルに保存しません。

### 承認を本文そのものに結び付ける

承認には、確認した下書きのSHA-256を記録します。本文が変わったら承認を取り消し、送信する本文が承認のハッシュと一致することをDBの制約でも確認します。認証は別の課題で、このハッシュは確認者の本人確認を行うものではありません。

## 障害時の動作とトレードオフ

LLMやSMTPの一時障害は待ち時間を増やしながら再試行し、断念した場合は失敗状態とアラートを記録します。workerが途中で停止したら、leaseの期限後に処理を引き継ぎます。

二重承認や通常の再実行では送信を重複させません。ただし、**SMTPがメールを受理した後、DBへ送信済みを記録する前に停止すると二重送信になります。** 同じMessage-IDで送りますが、Mailpitは両方を受け取ります。

送信前に送信済みと記録すると、同じ停止でメールを失うため、少なくとも1回の配送を選びました。これは完全な重複防止ではありません。解消するには、冪等性キーを受け付けるメールAPIなど、受信側の協力が必要です。停止条件はテストで再現しています。

## セキュリティ

すべてのポートはlocalhostに限定し、workerはMailpit以外のSMTPホストを拒否します。APIキーはGit管理外の`.env`へ置き、secret scanを実行します。

promptへは送信者の名前・メールアドレスそのものを入れず、ドメイン・企業・問い合わせ文を渡します。問い合わせ文はデータとして区切り、AI出力には構造と業務規則の検証をかけます。ログではメールアドレスを伏せ字にします。

承認画面では外部入力をHTMLエスケープし、iframe表示を拒否します。ただし**認証は未実装**なので、他の人が到達できる環境へ配備するには、認証・認可を先に追加する必要があります。

## 検証したこと

実PostgreSQLと実Mailpitを使って、並列の重複受付、複数worker、同時承認、9状態の81通りの遷移、DB制約を検証しています。意図的に防御を壊して、テストが失敗することも確かめました。公開用clean exportでは396件のテストがPASSしました。

実モデルの呼び出しは見込み度評価の60件と、workerを通したsmoke testの1件です。**返信案の作成と、一連の処理を通すE2Eはfake providerでのみ検証しています。**

検証で見つけ、修正した主な不具合は次のとおりです。

- メール検証ライブラリが、`@`より前の64文字制限を保証していなかった。
- SDKのエラー分類だけでは503・529を再試行対象として拾えなかったため、HTTP statusによる分類へ変更した。
- SMTPの受信者拒否で、一時的な4xxを恒久的な5xxと同様に扱っていた。
- 件名の改行によって、承認ハッシュへ渡す本文の区切りが曖昧になっていた。件名を1行に制限した。
- 送信成功直後のDB障害で、届いたメールを送信失敗と記録していた。
- n8n 2.xでは未publishのエラーworkflowが実行されず、アラートが失われる条件があった。
- 評価の費用見積もりがprompt全体のトークン数を十分に見ていなかったため、送信バイト数と余裕分を含める形へ修正した。
- LLMのNULが評価保存や呼び出し記録を失敗させた。下書きやAPIにも制御文字の扱いの不一致があり、正規化前に検証する共通規則へまとめた。

## 配備

同じMac上の隔離したLinux VM（Lima / Ubuntu 24.04）へ配備しました。開発用Dockerとは別で、ポート転送と共有フォルダを使いません。Mac側とVM側のイメージの内容をdigestで照合し、設定だけを変えます。

DBパスワードはVM内で生成し、Git外のrootだけが読めるファイルへ保存します。毎回のmigration、DBを含むhealth check、強制終了後の再起動、リクエストから送信までのログ追跡、lease後の回復を確認しました。公開デモURLはありません。

## 実測結果

2026年9月27日、合成問い合わせ30件を1人が事前に分類し、ラベルを固定して評価しました。各モデル1回、prompt `qualify-v1`、出力上限2048トークンです。[元レポート](../eval/reports/)

| モデル | 人の分類との一致 | 処理時間 p50 / p95 | 1件あたり費用 |
|---|---|---|---|
| Claude Sonnet 5 | 40.0%（12/30） | 4.4秒 / 8.3秒 | $0.0045 |
| Claude Haiku 4.5 | 43.3%（13/30） | 2.4秒 / 4.6秒 | $0.0011 |

問い合わせの種類ごとの一致件数は、各6件に対して次のとおりでした。

| 問い合わせの種類 | Sonnet 5 | Haiku 4.5 |
|---|---|---|
| 明確に見込みが高い | 5/6 | 5/6 |
| 明確に見込みが低い | 3/6 | 3/6 |
| 情報が不足 | 3/6 | 3/6 |
| 判断が境界付近 | 1/6 | 2/6 |
| 情報が矛盾 | 0/6 | 0/6 |

両モデルとも回答の検証を通過し、呼び出し失敗はありませんでした。不一致の多くは、人より見込み度を低く評価する方向でした（Sonnetは18件中17件、Haikuは17件中15件）。

このセットではHaikuが近い一致率で、処理時間は約半分、費用は約4分の1でした。ただし、30件・1人の分類・各1回の結果でモデルを一般的に順位付けすることはできません。特に情報が矛盾するケースを、次の評価で詳しく見る根拠になります。

**この一致率は見込み度評価だけの指標です。** 営業成績、返信文の品質、工数削減率を示すものではありません。

## 次に改善するなら

1. 承認画面と内部endpointへ認証・認可を追加し、他の人が到達できる環境への配備を検討する。
2. 問い合わせ数の増加に応じて、10秒pollをイベント通知へ変える。
3. 冪等性キーを受け付けるメールproviderで二重送信条件を解消する。
4. 企業情報補完のstubを実データ源へ置き換え、CRMへつなぐ。
5. 矛盾する情報を含む問い合わせを中心に、データ数・分類する人・反復回数を増やして評価する。
6. 実モデルによる返信案を、日本語を含めて評価する。
